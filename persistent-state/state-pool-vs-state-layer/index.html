vLLM persistent state · design comparison · 2026-11-20

State pool vs state layer

vllm#67374 keeps per-session state that tokens cannot rebuild in a state pool with its own scheduler, slot handles and release fence. Lucas Wilkinson's draft, pdtgct/vllm#6, keeps the same state as a Mamba state block that MambaManager allocates, plus one flag, ManagerConfig.recomputable. To test the draft, we ported the Nemotron ASR streaming plugin onto it and ran one round on an A40.

1 · Summary

Two ways to keep state that tokens cannot rebuild

Our state pool (#67374 at 2e7dfe972b)

  • A separate lifetime policy for state that tokens cannot rebuild.
  • PersistentStateSpec declares named components and their initializers.
  • StateScheduler and StateSlotManager own each slot; handles carry (epoch, slot, generation).
  • A release fence frees a slot only after the GPU confirms its last write.
  • Refuses async scheduling, runner CUDA graphs, prefix caching, parallelism and other options.

PR 6 state layer (4582db799d)

  • Ordinary requests over a Mamba state block, plus one flag.
  • A MambaSpec layer that MambaManager allocates.
  • The standard scheduler; slots come from the Mamba metadata builder's state indices.
  • No release fence: one stream orders every step's writes.
  • No refusals specific to state.

3 · Core gaps

Five gaps need a core change before the plugin can depend on PR 6

B1 to B5 need core changes; B6 and B7 are behaviour changes to agree on. B1, B2 and B4 come from reading the source; the round did not exercise them.

4 · Plugin changes

The plugin declares one Mamba layer and drops the features PR 6 cannot carry

The plugin's state is one MambaBase layer with one SHORT_CONV MambaSpec. It needs no state-pool code from core. CPU suite on build B before the frontend commits were added: 1,403 passed, 746 failed, 52 errors; the baseline passes 2,170. Every failure traces to a row below, to a deleted core API, or to the 12 route-guard tests that pass once the frontend commits are added.

What the port confirmed in PR 6's favour

  • Slot and freshness are equivalent: block_ids[0][0] is stable for a request's life, and num_computed_tokens == 0 matches the builder's has_initial_states_p.
  • The plugin needs no release fence under synchronous scheduling (see Release fence).
  • Budget-fit sizing with the startup floor matches the sizing we were considering for #67374.
  • The preemption raise cannot be reached in the plugin's layout: one state group in mode none, block_size >= max_model_len, no speculative decoding and no KV connector.
  • Core's /v1/realtime hook works: 16 of 17 tests pass, and the one failure is the dropped session factory.

6 · Lifecycle

One streaming session, start to finish

A /v1/realtime session is one resumable request that receives its audio in several inputs. Both designs keep the state page while the session waits for its next input. They differ in what the next input does and in when a closed session's page goes to another request.

7 · Release

Why PR 6 can drop the release fence

A slot is safe to reuse once nothing can still write to it for its previous owner. With every state write on the runner's main stream, CUDA runs step N+1 only after step N. Our fence exists for writes on other streams, which a model must register.

8 · Session length

Our request never grows; a PR 6 request grows with every input

Our StateScheduler replaces the prompt with each input, and the state page carries the history. PR 6 keeps upstream's session accounting: _update_request_as_session appends each input and every kept output token to the prompt, and drops an update that would exceed max_model_len with a warning (scheduler.py L1968–L2011 at main 07e4d6b957).

  • At --max-model-len 77000, with about one token plus the label tokens per 320 ms chunk, the token limit allows hours of audio.
  • Host memory and per-turn work bind first: the scheduler keeps every audio chunk, about 225 MiB per session-hour, and each turn re-sends the whole history (B3).
  • The bounded-history commit 566ef9259f trims consumed history, so a PR 6 request stays the same size, as ours does. At LibriSpeech lengths (at most 30.04 s) the round could not show the growth it removes.

9 · Model code

What the model writes

Both snippets are abridged from the stub model my_persistent_state.py in the test plugin.

Our state pool: declare a page, bind rows each step

# model class
supports_persistent_state = True
spec = PersistentStateSpec(
    descriptors=(
        PersistentStateDescriptor(
            "count", (1,), torch.int64, 0, 8, torch.zeros),
        ...),
    page_size_bytes=page_bytes)
self.state = PersistentStateLayerBase(spec, ...)

# ModelState.prepare_inputs, every step
rows = self.state_slots.bind_rows(
    STATE_LAYER, request_ids, handles)
count_pool = rows.component_pools["count"]
slot_indices = rows.slot_indices_cpu

PR 6: a Mamba layer that reads its metadata

# MambaBase layer
mamba_type = MambaAttentionBackendEnum.SHORT_CONV
def get_kv_cache_config(self, vllm_config):
    spec = MambaSpec(
        shapes=((1,),), dtypes=(torch.int64,),
        block_size=vllm_config.model_config.max_model_len,
        mamba_type=self.mamba_type)
    return MambaManager.layer_config(
        spec, recomputable=False)

# forward
md = get_forward_context().attn_metadata[self.prefix]
slots = md.state_indices_tensor_p[:md.num_prefills]
totals[slots] = totals[slots] * md.has_initial_states_p + ...

Under our design, the pool runs each component's initializer when a slot gets a new generation. Under PR 6, MambaManager does not zero new blocks, so the model applies has_initial_states_p itself; the flag is false when the request has no computed tokens. That flag is not enough for the plugin, whose first step does not write every state, so the port also initializes each new page (B7).
