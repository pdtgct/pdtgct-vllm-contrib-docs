vLLM persistent state · design comparison · 2026-11-20

Streaming-session designs for state that tokens cannot rebuild

Four designs for long-lived streaming sessions work at different layers. Two decide where per-session state lives; two change the streaming-session lifecycle of a request. PR 6's state layer is the preferred starting point, and a combined design takes its missing session lifecycle rules from the other three.

The comparison covers the #67374 state pool, the PR 6 state layer, resident sessions in vllm#68539 and bounded sessions in vllm#53879. It changed no code; the P3 proof of concept (PoC) that followed reproduces and fixes one gap, B2.

1 · Answer

The four designs work at different layers

  • Where per-session state lives. The state pool keeps it in a separate pool. The state layer keeps it in a Mamba KV group with recomputable=False.
  • The streaming-session lifecycle of a request. Resident sessions skip the per-chunk reinstall. Bounded sessions evict attention KV ranges and re-prefill.

Neither upstream item supplies storage, preemption protection or a recovery contract for state that tokens cannot rebuild, so neither replaces a state layer. Their lifecycle changes can still serve such state; the combined design below uses parts of both.

PR 6's state layer is the preferred architectural starting point. It is the smallest core change (+34 / −4 under vllm/), and it does not refuse async scheduling or CUDA graphs by design.

The evidence for it is narrow. One A40 round of an augmented PoC build gave the same transcripts. That build carried the #67583 model hooks, refused async scheduling in the plugin and turned off core's outer CUDA graphs. The round did not measure long sessions, worker request row exhaustion or the plugin under async scheduling.

PR 6 lacks session lifecycle rules. The combined design takes them from the other three designs:

SourceRules taken
State poolAdmission, idle reclaim, recoverable per-request failure
Resident sessionsIn-place resume
Bounded sessionsHost-history compaction, a logical position offset, the per-session prefix-cache rule, bounded output-processor state

Each rule needs a stated contract before it is general. The sections below name each contract, and the proposed gap coverage is not yet demonstrated. The #67374 state scheduler and page handles are not needed. A release-ordering rule is still needed (S7).

Settled rules:

  • The engine core marks the output that ends a state stream (EngineCoreOutput.terminal). The frontend ends a stream only on that mark.
  • State streams use DELTA output only. CUMULATIVE assembly belongs above the engine.
  • AsyncLLM refuses these sampling options on every input of a state stream: n > 1, stop strings, penalties, bad_words, prompt_logprobs, thinking_token_budget and custom logits processors. Structured outputs, refused at first, are allowed at de0b0bccdb with one grammar per stream.
  • AsyncLLM bounds pending inputs per stream with credits (max_pending_stream_inputs, default 8), not with errors.
  • An internal request id joins the external id, the client index, a per-instance nonce and a counter.

Duplex readiness (reviewed; implemented at de0b0bccdb)

vLLM-Omni's orchestrator drives each stage's engine core through StageEngineCoreClient, not AsyncLLM. The revision therefore splits the design into an engine-core contract and AsyncLLM policy. It adds core admission for an opening ADD that had no admit_stream call, a capacity report, and the declared resumable max_tokens stop. Two independent reviews returned changes required:

  • An empty continuation from a client that bypasses AsyncLLM fails an assert in the scheduler and stops the engine core. Core needs its own rule that ends that stream with an error.
  • An opening ADD that reuses a held request id merges into the held stream. Core must refuse it.
  • Core processes an explicit abort without publishing a terminal output, so a client that waits for the terminal mark can wait forever.
  • Admission should ride the opening ADD, which checks and reserves capacity in one step. The capacity report repeats max_num_active_reqs, which is fixed at startup.
  • Unique ids and the pending-input bound hold only for clients that follow a stated client protocol.

Implemented at de0b0bccdb (vllm/v1/engine/core.py:2145-2209): core ends a stream with an error on an input that carries no prompt tokens; an opening ADD that reuses a held request id ends the held stream with an error instead of merging into it; an explicit abort publishes a terminal output; and a stream is admitted with its opening ADD. The A40 round ran at ddf6db2ab8.

Both reviews passed the declared resumable max_tokens stop (TURN-012). The rules carry to 9503e3b878, whose A40 round passed every suite on 2026-11-26.

5 · Findings per design

Findings per design

Resident sessions (#68539)

  • Fast-path condition. _can_resume_in_place requires num_output_tokens >= max_tokens (the output budget was reached), an update with no prompt tokens, unchanged sampling params and none of the excluded features (scheduler.py:2061-2077). An EOS exactly at the budget qualifies; an EOS before it does not. Voxtral meets the condition with realtime_max_tokens = 1 at temperature 0. The plugin would qualify only if its turns used up their token budget and its updates carried no prompt tokens. Neither holds today.
  • What it bounds. It bounds what the scheduler sends to the workers per step, not the session. The scheduler-side Request keeps appending tokens, output tokens and mm_features. EngineCore keeps each original payload for replay, while the worker keeps metadata with consumed payloads set to None. B3 is unchanged.
  • G5. Not fixed. An early stop with a step in flight takes the fold path. With a token-less next update, the fold keeps the last sample, the stop token included, as a prompt token. For a Mamba group, that applies the stop token a second time, on top of G5's stale write.
  • Two resume paths with different sampling state. In place, the output history accumulates and max_tokens is incremented. On the fold, the history folds into the prompt and resets. Penalties and output-count logits processors therefore depend on which path ran. The review on the PR marks this P1.
  • Other review findings. P1: with token feedback gone, pending features per session have no limit; streaming_queue is an unbounded deque. P2: a structural realtime model that lacks the new attribute passes detection and then raises AttributeError in the frontend (connection.py:236-248).
  • Composition with the trim 566ef9259f. The two edit the same function, and the in-place branch returns before the trim. The trim cannot run in place without a worker turn-transition operation (S2). The two fixes are complementary, and neither subsumes the other.
  • What it avoids. The in-place path avoids the B2 transition (resumed but skipped while holding a worker request row) for eligible resumes; the fold path keeps it. B1, B4 and the abort concern raised in review stay open.

Bounded sessions (#51948, #53879)

  • Attention KV only. Range eviction (evict_token_range_for_request, kv_cache_manager.py:705-735) and consolidation both assume token-indexed KV that retained inputs can rebuild. A recomputable=False page has already absorbed the evicted tokens, and consolidation replays from tokens and pixels. That is the reason PR 6 raises on preemption.
  • Pieces that carry over, each with its own constraints:
    1. Host-history compaction (_compact_range, streaming/eviction.py:126-191) with per-input encoder-cache release (EncoderCacheManager.remove_input_ids, encoder_cache_manager.py:313-325). It is a general form of the PoC trim.
    2. A logical position offset. It is sent in NewRequestData and applied on the worker in a separate buffer (sched/output.py:56-93; model_states/default.py:259-285). It keeps model positions apart from compact storage positions. The mRoPE path keeps per-axis positions and replays eviction ranges, not a scalar offset (default.py:108-131).
    3. The prefix-cache rule. A bounded request neither looks up nor publishes prefix-cache blocks (request.py:253-268, 397-405). Retained KV carries the effect of discarded context, so hashing only the retained tokens would misidentify it.
    4. BoundedRequestState (streaming/output.py). It stops the output processor from accumulating each turn's output state.
  • A gap in the PoC. The output processor appends every update's prompt IDs (output_processor.py:266-267 at PR 6's head), and the trim leaves that unchanged. B3 is only half fixed.
  • Lifecycle. Validation and fold failures end one session with FINISHED_ERROR; eviction.py:108-113 still has an invariant RuntimeError. Preemption is a path of its own: it frees caches, resets progress and positions, and replays the surviving inputs (scheduler.py:1907-1939). It does not rebuild the transcript, as consolidation does (streaming/session.py:316-338), and no test covers it. A length stop parks the session, and the frontend replays the last token, which is precedent for PR 6's B6 behaviour. The HTTP adapter allows one active session per Python API server and requires one API-server process, which hides B2.
  • Why async scheduling and graphs are refused. Compaction runs in update_from_output and needs no step in flight. Evicted blocks are freed outside the deferred-free path. The 1D offset buffer would be ignored on FULL graph replay; this is inferred, not checked.
  • Hybrid models past the position horizon. The RFC thread establishes only that a uniform re-rotation (#45833) conflicts with a pinned attention sink. With a sink, the RFC compacts and re-prefills, which a state group cannot do.

State pool and state layer

State pool vs state layer compares these two. Two points matter here:

  • PR 6's single flag, recomputable, says only whether inputs can rebuild a group's cache. The scheduler uses it for preemption and the trim uses it for history. It says nothing about whether the model reads positions or whether sampling needs history.
  • The state pool's prompt replacement gives O(1) history without a position contract, because the plugin ignores positions.

6 · Combined design (sketch)

A streaming session is a long-lived request with declared contracts

At each input, the scheduler runs a retention policy over the request's KV groups. Each group and the model declare contracts, and the scheduler derives the session's rules from them. The sketch names the contracts it needs; it does not establish them.

S1. Explicit contracts instead of one flag

ContractDeclared byMeaning
ReconstructibleGroupRetained inputs can rebuild the group's cache. This is a new, stronger contract: PR 6's recomputable says only that a request's full inputs can rebuild it (kv_cache_interface.py:176).
Physically evictableGroupWhole blocks of a token range can be freed while the request lives.
Valid after evictionModelContinuing after eviction gives acceptable output.
Reads positionsModelThe forward consumes positions (1D or mRoPE).
History-dependent samplingSampling paramsPenalties, logits processors or grammars read past output.

Rules the scheduler derives from these contracts:

  • Preempt or consolidate only when every group is reconstructible.
  • Compact host history only up to the oldest token that any reconstructible group, the sampler or a connector still needs.
  • Apply a logical position offset only when the model reads positions; otherwise positions need no contract.

Each reconstructible group also defines its replay recipe: the retained inputs or checkpoint that rebuild it, and whether replay reproduces the existing state or establishes a new continuation state. #53879 records that retained KV depends on evicted history (request.py:256), so its consolidation establishes a new continuation state.

TP needs a stated state-ownership rule, sharded or replicated (is_kv_cache_tp_replicated, abstract.py:65 at PR 6's head); until one exists, TP stays outside the supported scope. The production design keeps TP at 1 today; TP above 1 is required and on the roadmap.

Sliding-window groups do not reduce to "the last window of tokens". A surviving KV entry can depend on earlier inputs through earlier layers, so it needs its own reconstruction rule. The same holds for attention interleaved with state that cannot be rebuilt.

S2. In-place resume through a turn-transition operation

  • A session whose worker request row is live resumes in place, as #68539 does.
  • A new worker operation runs the turn transition in order. It covers token storage; the CPU and GPU computed-token counts; the prompt and prefill boundaries, total_len and max_seq_len; output counters and penalty state; sampling params and processors; stale samples and drafts; model-specific state; and multimodal feature offsets and encoder input IDs, which #53879 rebases (streaming/eviction.py:146, 194), or else those layouts stay out of in-place compaction.
  • The operation spans three objects: request state (worker/gpu/states.py:37-125), sampler penalty state (penalties.py:35) and model state, which has its own update path. Today a cached update changes only the CPU computed-token count and appends block IDs (model_runner.py:1370-1389).
  • Dropping a token prefix and setting a logical position offset are part of that operation for groups that are not position-indexed storage. For attention groups, a prefix drop also needs block-aligned eviction and block-table replacement, because slot mapping uses local positions (block_table.py:396-427). Unsupported layouts stay on the fold path.
  • Output history is chunk-local on every path, which removes the in-place versus fold divergence (the first P1 finding in the #68539 review).

Sources: #68539, 566ef9259f and #53879's offset.

S3. Bounded host state and cache identity

  • Compaction drops consumed tokens and mm_features with their payloads once nothing that S1 lists still needs them.
  • A compacted session neither looks up nor publishes prefix-cache blocks, as in #53879.
  • KV and encoder connectors stay refused for compacted sessions until a transfer or checkpoint contract exists, as in the PoC trim.
  • The output processor resets per turn (BoundedRequestState).
  • Pending inputs per session are bounded, which answers the second P1 finding in the #68539 review.

Sources: #53879 and #58334.

S4. Session resource accounting

  • A session holds a worker request row, a state page and its KV blocks from admission to close.
  • The admission check counts held worker request rows, not waiting status, which addresses B2 for both resume paths.
  • Mandatory stream admission refuses a session beyond capacity, and the caller owns a session's lifetime, so idle reclaim is the caller's abort, not a core deadline. This addresses B4.

Source: #67375's rules, rebuilt on MambaManager.

S5. Recoverable per-request failure

  • The model reports a recoverable failure for identified requests, as StateSlotBindings.fail_requests does in #67374 (state_slots.py:219-227 at 2e7dfe972b).
  • Core retires those requests safely. The rule must define partial writes and completion identity.
  • A request that would need preemption of a group that is not reconstructible fails with an error instead of raising. The production design instead never preempts a state request; it waits (PSTATE-PRES-001).

The rule covers B1 for reported failures. It does not recover from arbitrary Python or CUDA exceptions, which stay fatal (engine/core.py:1769-1775 at PR 6's head).

S6. Stop tokens under async scheduling (hypothesis)

Contract: a per-row write-enable contract for state. On the GPU, the worker disables state writes for a row whose previous sample was a stop token, so the in-flight step writes nothing to that row's page. Ordinary single-token decode already has the previous sample on the device (input_batch.py:448-459).

Neither sentinel does this alone:

  • NULL_BLOCK_ID (0) skips a state-cache index in the causal-conv decode kernel (causal_conv1d.py:825-835).
  • PAD_SLOT_ID (−1) skips a sequence in the prefill launch mapping (utils.py:55-56).
  • Direct indexed writes honor neither: PR 6's stub (my_persistent_state.py:83-102, where −1 selects the last page) and Mamba2's state assignment (mamba_mixer2.py:973-994).

Obstacles:

  • A resumed turn's first row must not be disabled because the previous turn ended on EOS.
  • The mask must follow request slots through batch reordering.
  • Speculative decoding saves the last accepted sample, while the scheduler stops at the first stop token (input_batch.py:597-611; scheduler.py:2992-3004).
  • PP delivers samples through events (pp_utils.py:214-245).
  • FULL-graph metadata copies indices into persistent buffers (mamba_attn.py:598-651), so the mask needs graph-stable storage.
  • The plugin takes its page from host NewRequestData.block_ids, not from the builder's device indices.

The write-enable flag must reach the Mamba metadata builder's state indices and their persistent graph buffers (ReplaySSM's included), direct indexed writes in model code, and each plugin's host-side plan.

Scope a first version to single-token, non-speculative decode with explicit stop tokens. The fallback is to schedule no step past a possible stop for a group that is not reconstructible, which costs the async overlap for those rows.

S7. Release ordering

A freed page is safe to reuse only when every access by its old owner is ordered before the new owner's first conflicting access, including initialization, copies and connector loads.

  • One runner stream orders kernels on that stream.
  • PR 6 already defers freeing blocks when async scheduling or PP overlaps batches and a KV consumer connector could fill a reused page out of order (scheduler.py:212-226, 3318-3334).
  • A model that writes state on a second stream adds another case.

Core may skip a fence only where it can establish the ordering. A model's stream declaration is one input to that decision, not the whole rule. The PoC established the ordering only for the plugin under synchronous scheduling.

Source: #67374's fence, generalized.

7 · Gap coverage and trade-offs

Gap coverage and trade-offs

The coverage is proposed and not demonstrated, except for B2, which P3 reproduced and fixed in a PoC.

Trade-offs to decide

  • S2's turn-transition operation. It is a new runner interface with many fields. Without it, the trim forces the fold path and gives up #68539's O(1) transfer.
  • S1 against PR 6's single flag. S1 has more surface, but it separates preemption, eviction, positions and sampling history. A hybrid model (attention plus state) needs that separation.
  • B6, a length stop. Choose terminal or parked. If parked, also decide what happens to the visible final token, which the fold drops, and whether the model accepts the next input in mid-turn state. Chunk-local sampling history does not settle this.
  • Hybrid sessions past the position horizon. None of the compared implementations provides a verified rule for a hybrid model with a pinned sink. Ending the session at the horizon is the conservative fallback, not a proven necessity.
  • S6 against refusing async scheduling. S6 keeps the overlap but adds a write-enable duty to every state kernel and plugin. Refusing async scheduling is simple and costs throughput not yet measured for this plugin.

Admission counted only len(running) plus num_waiting_for_streaming_input (scheduler.py L1103), so a step that skips the resumed session admits another request beyond max_num_active_reqs, and the worker's assert len(self.free_indices) > 0 fails. Stub tests that drive the real Scheduler reproduce it: on main without the fix, three over-admission tests fail with "No free indices". The fix, local commit c87b748246 on branch poc/pr6-admission-rows-20261120 (not pushed), tracks resumed sessions that hold a row in resumed_streaming_sessions and covers the fold path only.
