Persistent state · landscape

Persistent state in vLLM: a maintainer's guide to the landscape

The proposal is the right design for sessions that keep state tokens cannot rebuild, such as streaming ASR: it keeps PR 6's small storage change and adds the nine rules the state pool showed are needed, without refusing async scheduling or CUDA graphs. Bounded sessions remain the right design for hours-long attention sessions, and the proposal neither helps nor harms them. Hybrid and full-duplex models need both at once, which no design covers yet; one turn transition with a retention policy per KV group would.

1 · Memory

Memory architectures and layouts

Read this section first if you are new to vLLM's memory model. Every design in this guide uses the same GPU allocation, the KV cache. The designs differ in three things: what kind of page a session holds, who may take that page back, and what grows in host memory on every turn.

How vLLM builds its KV cache

At startup, core builds the KV cache in a fixed order. The diagram source is below it.

Diagram source
flowchart TD
    W["Load weights"] --> P["Profile one forward pass at the largest batch"]
    P --> G["Capture CUDA graphs"]
    G --> B["KV cache budget = what is left under gpu_memory_utilization"]
    B --> S["Group layers by spec: full attention, sliding window, Mamba state"]
    S --> U["Make every group's page the same byte size"]
    U --> BP["One block pool of equal pages"]
    BP --> M1["FullAttentionManager: one block per block_size tokens"]
    BP --> M2["SlidingWindowManager: frees blocks behind the window"]
    BP --> M3["MambaManager: a fixed number of pages per request"]
    M1 --> T["Per-request block table, one per group"]
    M2 --> T
    M3 --> T
    T --> R["Worker: max_num_seqs rows of per-request tables"]
    R --> K["Kernels read KV and state through the block tables"]
  1. Budget. Core profiles a forward pass and captures CUDA graphs, then gives the KV cache whatever memory remains (vllm/v1/worker/gpu_worker.py:828-832 at PR 6). The KV cache is therefore sized by leftover memory, not by a configured count, unless a design overrides it.
  2. Groups. Layers with the same cache spec form a KV cache group, and each group has one manager class. A hybrid model has at least two groups, for example full attention and Mamba.
  3. One page size. All groups draw pages from one block pool, so core makes their page sizes equal: an attention group raises its block size, and a Mamba page is padded (unify_kv_cache_spec_page_size, vllm/v1/core/kv_cache_planning.py:331 at PR 6).
  4. Block tables. Each request holds one block table per group, a list of page ids. Attention kernels read K and V through it (paged attention), and Mamba kernels read and write the request's state page through it.
  5. Worker rows. The model runner keeps a fixed number of per-request rows, max_num_seqs (vllm/v1/worker/gpu/model_runner.py:243). CUDA graphs capture the addresses of these buffers, so the buffers must not move while a graph that uses them exists.

Three differences carry most of the consequences in the rest of this guide:

  • Who may take a page back. Only attention pages may be preempted or evicted. Once a group holds state that tokens cannot rebuild, PR 6 rules out preemption for the whole request, including its attention blocks.
  • Configured or leftover size. The state pool fixes the cache at max_num_seqs + 1 pages and fails at startup if they do not fit. PR 6 and the proposal take all leftover memory, so admission, not sizing, must stop over-subscription.
  • Host growth. GPU cost per session is constant in the state designs. What grows is host history, and only the proposal and bounded sessions bound it.

2 · At a glance

At a glance

Read it top to bottom: a lifecycle design decides what happens between inputs, and a storage design decides where the session's data lives. Three lifecycle designs sit on rebuildable attention KV; the proposal's rules sit on PR 6's state layer. The state pool does both jobs in one separate component.

3 · Designs

The designs in plain terms

Five designs touch long-lived sessions in vLLM. Two decide where state lives; three decide how a session moves from one input to the next. They are not rivals in every case: they answer different questions.

The problem they share. vLLM's KV cache is rebuildable: if the engine throws a request's blocks away (preemption), it can recompute them from the tokens. A streaming speech model keeps something else per session (encoder caches, decoder state, emission progress) that no token sequence can rebuild. Losing it, or letting another session read it, breaks the transcript. A long session also accumulates history, and every design must stop that from growing without bound.

DesignOne-line ideaDecides where state lives?Decides how a session resumes?
State pool (vllm#67374, with #67375 and #67583)A separate pool of state pages with its own scheduler that binds, parks and retires themyesyes: replaces the prompt on every input
State layer (pdtgct/vllm#6, "PR 6")Put the state in a Mamba-style KV cache group that the normal allocator owns, and mark it not rebuildableyesno: uses upstream's streaming-session update
The proposal (PF-1 to PF-9)PR 6, plus nine rules that make that group safe for long sessionsyes, via PR 6yes: rules for turn end, compaction, admission, failure
Bounded sessions (vllm#53879)Keep hours-long attention sessions within a token budget by evicting old KV and re-prefillingno: attention KV onlyyes: eviction, compaction, position offset
Resident sessions (vllm#68539)Skip the per-chunk reinstall: a session with a live worker row resumes in placeno: attention KV onlyyes: in place when the output budget was reached

Where the proposal sits. It is not a sixth mechanism. It takes PR 6's storage (the smallest core change, +34 / −4 lines under vllm/) and adds the lifecycle rules the state pool proved necessary: admission, idle reclaim, per-request failure, page initialization, release ordering, a turn-end rule and bounded history. It borrows compaction and the logical position offset from bounded sessions, and the in-place resume idea from resident sessions.

4 · Features

Feature comparison for maintainers

The proposal is a different trade from the state pool, not a strict superset: it aims for the pool's safety guarantees while keeping async scheduling, CUDA graphs and the ordinary scheduler. Its column is a design; every other column is code read at the heads named under How this was checked.

Four rows carry the decision:

  • Async scheduling and CUDA graphs. The state pool refuses async scheduling for everyone, and runner graphs. PR 6 allows both but writes a stop token into state under async (G5). The proposal keeps both with a per-request barrier, so only rows with state lose overlap.
  • History bounded. The state pool replaces the prompt in the scheduler, but its output processor still appends prompt ids for requests that skip stream admission (vllm/v1/engine/output_processor.py:311 at the pool's head). PR 6 grows the prompt every turn. The proposal requires a bound in every layer.
  • One session fails. On PR 6 a failing row raises and the engine stops for every client. The state pool and the proposal let the model report the failed request, which finishes alone.
  • Preemption. Attention designs replay; state cannot be replayed, so the state pool and the proposal end the request instead, where PR 6 raises.

The proposal also relaxes one state-pool guarantee on purpose: the pool ends a session on every stop but EOS (vllm/v1/core/sched/state_scheduler.py:307), and PF-5 lets a model declare a length stop resumable. That is safe only if the watermark holds.

5 · Use cases

Thought experiments: the proposal applied to each use case

Two facts decide which design a use case needs: whether it keeps state that tokens cannot rebuild, and whether its sessions outgrow max_model_len so that attention KV must be evicted. The proposal answers the first and refuses the second; bounded sessions answer the second and refuse the first. Nobody yet answers both.

Why bounded sessions are a neighbour. The proposal knows two kinds of memory: ordinary rebuildable KV, and state that must never be evicted or recomputed. Bounded-session KV is a third kind: rebuildable from the retained window, and evicted on purpose. Its code refuses any layout but one full-attention group (vllm/v1/streaming/session.py:120-123 at #53879), so a state group never reaches it, and the proposal neither helps nor harms it.

Why resident sessions need one more requirement. Voxtral's turns end on a length stop, so under PF-5 Voxtral must declare that stop resumable, and the watermark then does real work under async scheduling. But the proposal leaves the resume path open (PF-6, in place or fold), and #68539's whole value is keeping the worker row (vllm/v1/core/sched/scheduler.py:2010-2024 at #68539).

Why hybrid and duplex fall in the gap. At PR 6's head, one not-rebuildable group makes the whole request unpreemptable, and core reserves each active request's largest footprint across every group (vllm/v1/core/sched/scheduler.py:146-162 at PR 6). For a hybrid model that means full-length attention KV per slot. Continuing past the horizon needs attention eviction while the page stays, which is a non-goal today.

The single biggest weakness. One axis and one lifetime rule: declared state is never evicted, everything else is ordinary KV. Three of the six cases keep attention KV that must be evicted beside a page that must not be. The fix the researchers point to is per-group retention, described under Guidance.

Three things a maintainer may not expect, all read in code at PR 6's head.

  1. A resumed session is invisible to admission. The fold sets the request to WAITING and decrements the parked count (scheduler.py:2041-2043), but the worker keeps its row until finish or preemption (vllm/v1/worker/gpu/model_runner.py:1278-1291). One skipped step lets admission take a new request and the worker's free-row assert fails. This is upstream bug B2, fixed on branch 0a09c28165.
  2. Every turn is a new request to the worker. The scheduler re-sends a resumed request in full, and the runner removes and re-adds its row (model_runner.py:1313-1316). Only the page stays constant.
  3. Sleep can silently zero parked state. A keep pause retains requests (vllm/v1/engine/core.py:1055); sleep releases the cache's physical pages, and wake maps fresh zeroed pages (vllm/v1/worker/gpu_worker.py:364-368, :393-396). The scheduler still believes the pages hold state, so the model continues from zeros. Each link is verified; the end-to-end case was not run. PF-2 forbids sleep while state is held.

7 · Memory placement

Where state memory sits

A session's GPU cost is one page and never grows; its host cost is what grows, in four places. State pages live in the same KV cache region as attention blocks, so the KV cache manager, not a separate pool, owns their capacity.

  • GPU. A page's size is the sum of the model's declared state shapes. At startup core profiles a forward pass, captures CUDA graphs and then gives the KV cache region what is left (vllm/v1/worker/gpu_worker.py:828-832 at PR 6). That is why PR 6 allocated 6,439 pages on an A40 where the state pool allocated 65: budget-fit sizing against a fixed pool. The extensible KV cache reserves address space for every block and commits physical memory as needed, so addresses never move (vllm/v1/worker/extensible_kv_cache.py:80-82).
  • Host. On PR 6 every turn appends to four structures, about 20 KiB per 320 ms chunk or 225 MiB per session-hour in the scheduler alone. PF-6 bounds each to the new input; the state pool already bounds the scheduler's copy but not the output processor's.
  • Where the two meet. A page is GPU memory the scheduler accounts for in blocks; history is host memory nothing accounts for today. Pool sizing (budget-fit with a max_num_seqs + 1 floor) is an open decision in the requirements doc.

8 · Guidance

Guidance per use case

Build the proposal for state that tokens cannot rebuild, leave bounded sessions as they are for attention KV, and close the gap between them with one turn transition that applies a retention policy per KV group. Retention policy is what makes hybrid and full-duplex models possible; it is a direction, not part of the current proposal.

The watermark alone does not join the two. Bounded sessions re-prefill by freeing the whole request and recomputing it from a rebuilt transcript (vllm/v1/streaming/session.py:321-331 at #53879), which would also free a hybrid model's state page. Skipping state writes during that replay does not help: a Mamba layer computes its outputs from the state it reads, and the current state already includes the replayed tokens. A hybrid session can use eviction with its state page kept, but until a reconstruction policy is designed it must end before any re-prefill, including one forced when eviction cannot free enough whole blocks.

Order of work this suggests. First the proposal for streaming ASR, since it has a consumer, a baseline and measured gaps. Second, decide the resume path (in place or fold) with resident sessions in mind, since two use cases depend on it. Third, per-group retention, which needs bounded sessions' authors and a hybrid model to test against.

10 · Requirements

The nine requirements (PF-1 to PF-9)

Each requirement states an outcome. The text is the requirements document's Generic feature requirements table as it stood on 2026-11-22.

ID and nameRequirement
PF-1 DeclareA model declares each state component (shape, dtype, initial value), that its inputs cannot rebuild it, its tensor-parallel ownership, and which history it needs to continue: positions, if it reads them; past output, if its sampling params read it. It also declares its startup prerequisites: whether it captures its own graphs, what that capture needs, and which synthetic warmup inputs it accepts.
PF-2 PreserveA request holds its state exclusively from first schedule until it finishes by any path. Core performs no operation that loses, duplicates or rebuilds it (preempt, evict, recompute, prefix-share, cache reset, sleep), and the storage, layout and addressing a graph captured stay valid until that graph is retired, or the graph is invalidated and recaptured before its next replay.
PF-3 Bound the pageA new page holds its declared initial value before its first read. A page is reused only after every access by its previous owner is ordered before the new owner's first access, on every finish path.
PF-4 Exactly onceCommitted input changes state once and in order. Nothing else changes it: not a sample after a stop, a resume replay, a warmup or profiling input, or input cancelled before it ran. Profiling, warmup and capture neither change nor read live state.
PF-5 Turn boundaryA request parks only at a stop the model declares resumable. Any other end (length, position horizon, abort) finishes it. A model may declare a length stop resumable, as resident sessions (#68539) need.
PF-6 Length independencePer-turn work, transfer and retained host memory in every engine layer are O(new input): scheduler request, output processor, original payloads, encoder features and the pending-input queue.
PF-7 Account and reclaimAdmission counts every resource a live request holds, running or parked, and refuses at open when one is exhausted. Every held resource has a bounded path back to free: deadlines for a stream never fed, parked idle or draining, and client abort.
PF-8 Fail one requestA failure attributable to one request, reported by the model or forced by PF-2, finishes that request with an error; every other request continues. The rule defines what a partial write leaves in the page and which completion the failure belongs to. Arbitrary Python or CUDA exceptions stay fatal.
PF-9 Start and resume safelyCore honors a model's declared profiling, warmup and capture prerequisites, so a model may decline synthetic inputs it does not support in favour of a supported preparation path, and counts retained allocations and transient peaks before final page sizing. Before serving after startup, wake or cache reset, core makes the required execution resources and graphs ready and consistent with PF-2 to PF-4.
