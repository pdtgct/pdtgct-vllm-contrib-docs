Persistent state · landscape

Persistent state in vLLM: a maintainer's guide to the landscape

Upstream vLLM already has long-lived sessions: streaming input (#28973) keeps one request alive across input chunks, and the Realtime API is built on it. What upstream lacks is, in RFC #51948's words, memory management for sessions: nothing admits a session against capacity, reclaims an idle one, bounds its history, or protects state that tokens cannot rebuild. Five open designs each fill part of that gap.

Recommendation. Build the proposal (PR 6's state layer plus nine rules, PF-1 to PF-9) for state that tokens cannot rebuild, such as streaming ASR. It keeps async scheduling and CUDA graphs, which the state pool refuses. Leave bounded sessions (#53876, #53879) as the design for hours-long attention sessions. Hybrid and full-duplex models need both at once, which no vLLM design covers yet. The join is one turn transition with a retention policy per KV group, the model SGLang already uses: its radix cache evicts full-attention, sliding-window and Mamba data as separate components under cascade rules.

Full duplex. vLLM-Omni's full-duplex runtime is a session layer above the engine core, and it drives each stage's engine core through its own client, not AsyncLLM. The proposal therefore states its safety rules as an engine-core contract that any client gets, with AsyncLLM policy as a separate layer. Core owns state pages, worker rows and their safety rules; the session layer owns identity, deadlines and conversational policy. The proposal can then serve PersonaPlex's Stage 0, which stops on a one-token length limit after every frame, through a declared resumable max_tokens stop.

1 · GPU memory

How vLLM manages GPU memory today

Every design in this guide uses one GPU allocation, the KV cache. The designs differ in three things: what kind of page a session holds, who may take that page back, and what grows in host memory on every turn. At startup, core builds the cache in this order:

  • Budget. Core gives the KV cache whatever memory remains after profiling and graph capture (vllm/v1/worker/gpu_worker.py:828-832 at PR 6), so the cache is sized by leftover memory, not by a configured count. The extensible KV cache, completed in Q4 2026, reserves address space for every block and commits physical memory as needed, so block addresses never move (vllm/v1/worker/extensible_kv_cache.py).
  • Groups and one page size. Layers with the same cache spec form a KV cache group, and each group has one manager (full attention, sliding window or Mamba). All groups draw pages from one block pool, so core makes their page sizes equal: an attention group raises its block size and a Mamba page is padded (hybrid KV cache manager design). A model can declare its own grouping (SupportsKVCacheGrouping), and a platform can replace placement with a KVCacheConfigBuilder, an interface the code marks experimental (vllm/v1/core/kv_cache_config_builder.py).
  • Block tables and worker rows. Each request holds one block table per group, through which kernels read attention KV and read and write state pages. The model runner keeps max_num_seqs rows of per-request tables, and CUDA graphs capture these buffers' addresses, so the buffers must not move while a graph that uses them exists.
  • Prefix caching per group. A hybrid request's cache hit is the intersection of each group's hit, and the hybrid coordinator handles exactly two attention types, full attention plus one other. Mamba state is cached only at block boundaries, so a hit resumes at a boundary (automatic prefix caching).

2 · Streaming input

Streaming input upstream, and what it lacks

AsyncLLM.generate() accepts an async generator of StreamingInput objects. The first chunk creates an anchor request that lives for the session, and later chunks queue on it in order (Streaming Requests & Realtime API in vLLM). When a turn stops, the scheduler folds the next chunk into the anchor: it appends the turn's output, minus the last sampled token, and the new input to the prompt, and returns the request to the waiting queue. The session's KV blocks stay allocated between chunks, so a new chunk costs only its own tokens. This document calls that resume the fold path.

The mechanism has three gaps for long sessions:

  • Nothing reclaims an idle session. The blog states that vLLM does not preempt idle streaming sessions, so an open session holds memory no other request can use. #59339 (open) reclaims blocks from parked sessions under KV pressure, after parked sessions were shown to deadlock the scheduler by holding every block.
  • History and positions grow. The prompt and the position counter grow every turn until the session ends or reaches max_model_len. Bounded sessions address this for attention KV.
  • Every resume re-sends the request. The fold returns the request to waiting, so the scheduler re-sends it to the worker with its full token history and features, a per-step cost that grows with the session. #68539 resumes in place and reports 24 concurrent 20-minute Voxtral sessions per H100 under async scheduling, against 1 on main.

SIG Core's Q4 2026 roadmap lists streaming-input reliability as open work. Four open issues show where the lifecycle breaks today:

IssueFailure
#69139The scheduler admits past max_num_seqs when it skips a resumed session, and the worker asserts "No free indices"; the same failure as gap B2 in the PR 6 proof of concept.

#49449Rebuilding a session leaves stale prefix-cache block hashes and can produce incorrect output.
#54215AsyncLLM appends later chunks' tokens to the caller's prompt list in place.

All of these assume rebuildable KV: the remedy for memory pressure is preemption, which recomputes from tokens. A model whose session state tokens cannot rebuild needs a different contract, which is what the state designs supply.

The proposal is not a sixth mechanism. It takes PR 6's storage, the smallest core change (+34 / −4 lines under vllm/), and adds the lifecycle rules the state pool proved necessary. It borrows compaction and the logical position offset from bounded sessions and the in-place resume from resident sessions. The consequential difference is reclaim: once a group holds state that tokens cannot rebuild, PR 6 rules out preemption for the whole request, its attention blocks included. Because PR 6 and the proposal also take all leftover memory, admission, not sizing, must stop over-subscription.

The proposal sets no deadline in the engine core. The client that opened a stream owns its lifetime: it closes or aborts the stream, and AsyncLLM aborts a stream whose input or output side ends without a close. A serving layer that wants an inactivity timeout enforces it by aborting, so no stream has two reapers.

4 · State memory

Where state memory sits

A session's GPU cost is one page and never grows; its host cost is what grows, in four places. State pages live in the same KV cache region as attention blocks, so the KV cache manager, not a separate pool, owns their capacity.

  • GPU. A page's size is the sum of the model's declared state shapes. At startup core profiles a forward pass, captures CUDA graphs and then gives the KV cache region what is left (vllm/v1/worker/gpu_worker.py:828-832 at PR 6). That is why PR 6 allocated 6,439 pages on an A40 where the state pool allocated 65: budget-fit sizing against a fixed pool. The extensible KV cache reserves address space for every block and commits physical memory as needed, so addresses never move (vllm/v1/worker/extensible_kv_cache.py:80-82).
  • Host. On PR 6 every turn appends to four structures, about 20 KiB per 320 ms chunk or 225 MiB per session-hour in the scheduler alone. PF-6 bounds each to the new input; the state pool already bounds the scheduler's copy but not the output processor's.
  • Where the two meet. A page is GPU memory the scheduler accounts for in blocks; history is host memory nothing accounts for today. Pool sizing (budget-fit with a max_num_seqs + 1 floor) is an open decision in the requirements doc.

5 · What decides

What decides between them

The proposal is a different trade from the state pool, not a strict superset: it aims for the pool's guarantees while keeping async scheduling, CUDA graphs and the ordinary scheduler. In the grid, the proposal's column is the design; every other column is code read at the heads under How this was checked.

Four rows carry the decision:

  • Async scheduling and CUDA graphs. The state pool refuses async scheduling engine-wide, and runner graphs. PR 6 allows both but writes a stop token into state under async (G5). The proposal keeps both with a per-request barrier: the scheduler does not schedule a state request while it has tokens in flight, so only rows with state lose overlap.
  • History bounded. The state pool bounds the scheduler's copy, but its output processor still appends prompt ids for requests that skip stream admission (vllm/v1/engine/output_processor.py:311 at the pool's head). PR 6 grows the prompt every turn. The proposal requires a bound in every layer.
  • One session fails. On PR 6 a failing row raises and the engine stops for every client. The state pool and the proposal let the model report the failed request, which finishes alone.
  • Preemption. Attention designs replay; state cannot be replayed, so the state pool and the proposal end the request where PR 6 raises.

The proposal relaxes one state-pool guarantee on purpose: the pool ends a session on every stop but EOS (vllm/v1/core/sched/state_scheduler.py:307), and PF-5 lets a model declare its per-turn max_tokens stop resumable. Under the per-request barrier this needs no watermark: the fold discards the turn's last sampled token, and no step runs past the stop. A stop at the position limit always ends the stream.

6 · Status

Where the proposal stands (2026-11-23)

The proposal is written as EARS specs (prefix PSTATE) and implemented on pdtgct/vllm branch pstate-impl-20261122 at ac2ef47540: upstream main 842f74fa8d plus PR 6's net diff, the hooks-only re-cut of #67583 and the #69139 fix, +1,390 / −66 lines under vllm/ in 33 files. This head passed its A40 GPU round on 2026-11-23 (ten suites, 798 test cases, 0 failed, 0 skipped). State pool vs state layer maps each PoC gap to its rule.

Rules settled on 2026-11-23:

  • No deadlines in the engine core. The caller owns a stream's lifetime. AsyncLLM aborts a stream whose input task or output generator ends without a close, and fails every open stream if the engine core dies.
  • The engine core marks the end. EngineCoreOutput.terminal marks the output that ends a state stream; a frontend ends a stream only on that mark.
  • DELTA output only, as AsyncLLM policy. CUMULATIVE assembly belongs above the engine.
  • Recompute recovery is refused for state models; the per-request barrier always applies, and an opt-out for models that ignore stopped-row echoes is deferred.
  • Pending inputs are bounded by credits (max_pending_stream_inputs, default 8), not by errors.

Settled for duplex readiness: an engine-core contract that holds for every client of the engine-core process, not only AsyncLLM, so that vLLM-Omni's stage clients get the same guarantees (see vLLM-Omni full duplex below). Core drops a continuation it does not hold as a stream, ends a held request when an opening request reuses its id, refuses an input it cannot fold (no token ids, prompt embeddings, or a continuation that changes the stream's structured outputs; a stream keeps one grammar from its opener, not reset per turn, and a grammar that fails to compile or rejects a token ends the stream terminally) with a validation error instead of failing an assert, publishes a terminal output on an explicit abort, and admits a stream with its opening request, reserving its row in the same step; one fixed order resolves competing conditions. A model may declare its per-turn max_tokens stop resumable.

Two behaviors a maintainer may not expect, all read in code at PR 6's head:

  • A resumed session is invisible to admission. The fold sets the request to WAITING and decrements the parked count, but the worker keeps its row until finish or preemption. One skipped step lets admission take a new request, and the worker's free-row assert fails. The PR 6 proof of concept called this gap B2; upstream now tracks it as #69139, and the proposal's admission counts the held row (PF-7).
  • Sleep can silently zero parked state. A keep pause retains requests, sleep releases the cache's physical pages, and wake maps fresh zeroed pages (vllm/v1/worker/gpu_worker.py:364-368, :393-396), while the scheduler still believes the pages hold state. Each link is verified; the end-to-end case was not run. PF-2 forbids sleep while state is held.

What this means for the proposal:

  • Ordered reuse (PF-3) is an established rule. SGLang's unified memory states it directly: freeing is logical at once, but a freed page is not reused until the forward that may still touch it has been processed (mem_cache/README.md).
  • Refusing at open (PF-7) matches both speech runtimes. SGLang's realtime ASR refuses a session past its cap with a too_many_sessions error; vLLM-Omni's duplex runtime caps sessions at open and owns its sessions' deadlines through idle leases and a reaper, the job the proposal leaves to the layer above the engine core.
  • Per-group retention has a working model. SGLang's radix cache evicts full-attention, sliding-window and Mamba data as separate components with cascade rules: evicting a full-attention node evicts its sliding-window and Mamba data, and evicting Mamba data touches nothing else. Its streaming sessions keep deferred KV private and do not publish it to the prefix tree at turn end (server arguments), which matches the proposal's choice to turn prefix caching off for state requests.
  • Sizing remains the open decision. SGLang documents a cliff when the state pool is sized for concurrency in multi-turn traffic: on one agent trace, moving memory from state slots to KV raised the prefix-hit rate from 0.06 to 0.89 and output throughput 4.8-fold. vLLM's single pool avoids a ratio to tune, but leaves state pages and attention blocks competing for one budget, so PF-7's admission is the only guard. Whether to add a state-page cap is still open; the new KVCacheConfigBuilder is the natural place to express one without a second pool (an inference, not tested).

9 · Full duplex

vLLM-Omni full duplex: two layers, one interface

vLLM-Omni's full-duplex runtime and the proposal work at different layers. The runtime is a session layer in Omni's orchestrator: it owns session identity, epochs and barge-in, a lease (idle TTL, disconnect grace, resume), service-level admission and history policy. The proposal is a layer in the engine core: it decides where state that tokens cannot rebuild lives, who may reclaim it, how writes stay exactly-once and how one request fails without stopping the engine. Omni needs the second layer and today builds it separately in each model: PersonaPlex keeps its streaming encoder state in codec rows that the model owns, sized by max_sessions and outside the KV cache, and five of the seven duplex plugins advertise supports_model_internal_state=True.

The orchestrator drives each stage's engine core through StageEngineCoreClient, a subclass of the engine-core client, not through AsyncLLM. Every safety rule that duplex needs must therefore hold in the engine core for any client; AsyncLLM rules such as sampling refusals and pending-input credits stay frontend policy.

  • Identity. Omni's stage request id already encodes session and epoch (duplex-s.<session>.e.<epoch>.r.<role>), so one core request is one (session, epoch), and a new epoch is a new request with a freshly initialized page. PF-1 to PF-3 need no change for barge-in. Unique ids are a client precondition; core refuses an opening request that reuses a held id.
  • Capacity. Core counts pages and worker rows, and Omni's max_sessions becomes a service cap at or below what core can hold. Until the two are tied, a refusal at the first append must surface as a typed open failure, not a stage error.
  • Deadlines. The engine core sets none, so Omni's lease is the only reaper; it enforces expiry by aborting the request.
  • Failure. PF-8 turns a model's reported failure into a finished request, and Omni's forward-failure path then closes that session alone. A PersonaPlex session spans two engines (Stage 0 and Stage 1), so the session layer closes the other half.

How PF-1 to PF-9 hold for duplex: PF-1, PF-2 (within an epoch), PF-3, PF-8 and PF-9 hold as written. PF-5 holds once Stage 0 declares its one-token max_tokens stop resumable. PF-7 holds with deadlines owned by the session layer. PF-6 holds for the state group only: attention KV still grows by at least one position per frame, 45,000 per hour at 12.5 frames per second, so an open-ended session ends at max_model_len until per-group retention exists. PF-4 holds at a cost: with one sampled token per frame, every step ends at a stop, so the per-request barrier removes async overlap for every duplex row (an inference, not measured). The fix is a declared alternative in which state advances only for a new input identity (epoch, seq), which Omni's runtime already enforces; it is exactly-once only for state that advances from new input alone, as PersonaPlex's encoder rows do.

Recommended path. Omni adopts state groups (bottom-up), keeping its session layer for conversational policy: state storage and its safety rules move into core for every model. A core-owned session with a KV lease that survives barge-in, as Omni's closed RFC #3745 proposed, becomes the target only if keeping context across barge-in becomes a requirement; PersonaPlex discards that context today. As a first pilot, after the streaming-ASR version lands, declare PersonaPlex's Stage 0 encoder rows as one state group and check on an A40: session capacity against Omni main, a forced preemption, and parity of the first 60 s of audio output. Nothing in this section was run; the PF-4 overlap cost and the preemption hazard are inferences.

10 · Roadmap

Roadmap alignment

No item in the Q4 2026 roadmap names persistent state, but six items decide where the proposal can land and what it can reuse. SIG Core's Q2 2026 plan had already named a KV cache manager rethink (PyTorch Conference EU 2026 slides).

Two consequences follow. First, the proposal should be offered as part of SIG Core's streaming-input reliability work, not as a separate feature, since its admission and lifetime rules fix bugs that work already tracks. Second, per-group retention needs the scheduler redesign or an equivalent change; it should not be built on today's fold path.

11 · Guidance

Guidance per use case

Two facts decide which design a use case needs: whether it keeps state that tokens cannot rebuild, and whether its sessions outgrow max_model_len, so that attention KV must be evicted. The proposal answers the first and refuses the second; bounded sessions answer the second and refuse the first.

Hybrid and full-duplex models fall in the gap because PR 6 makes the whole request unpreemptable once one group is not rebuildable, and core reserves each active request's largest footprint across every group (vllm/v1/core/sched/scheduler.py:146-162 at PR 6), which means full-length attention KV per slot. The fix is one turn transition with a retention policy per KV group:

The watermark alone does not join the two halves. Bounded sessions re-prefill by freeing the whole request and recomputing it from a rebuilt transcript (vllm/v1/streaming/session.py:321-331 at #53879), which would also free a hybrid model's state page. Skipping state writes during that replay does not help: a Mamba layer computes its outputs from the state it reads, and the current state already includes the replayed tokens. Until a reconstruction policy exists, a hybrid session may evict attention blocks with its state page kept, but must end before any re-prefill.

Order of work. First, the proposal for streaming ASR, offered within SIG Core's streaming-input reliability work, since it has a consumer, a baseline and measured gaps; its engine-core contract keeps vLLM-Omni's stage clients in scope. Second, decide the resume path (in place or fold) with the resident-sessions authors, since two use cases depend on it. Third, the PersonaPlex Stage 0 pilot with vLLM-Omni. Fourth, per-group retention, with the bounded-sessions authors and a hybrid model to test against.

Left out on purpose, and when to add each

The proposal already lets a model declare its per-turn max_tokens stop resumable; under the per-request barrier that needs no watermark. These extensions stay out until a consumer needs them:

ExtensionAdd it whenShape
State-applied watermarka model parks on a length stop, replays its last reply token and keeps async overlapa per-request count of tokens the state already includes; tokens below it skip the state layers
Exactly-once by input identitya model with one sampled token per frame, such as PersonaPlex's Stage 0, needs async overlapstate advances only for a new input identity (epoch, seq); valid only for state that advances from new input alone
In-place resumea consumer needs O(1) resume transfer or keeps per-row worker state across turnsa worker turn transition that keeps the row
Tensor and data parallelism above 1a state model needs more than one GPU, or a stage runs behind a data-parallel clientreplicated state, with failure reports agreed across ranks; admission rides the opening request, which a data-parallel client routes to one engine
Per-group retentiona hybrid or full-duplex model runs past max_model_len, or must keep context across barge-inone turn transition with a retention policy per KV group, plus a reconstruction policy for re-prefill

In every version, a session that reaches max_model_len ends.

Acceptance, chunk sizes and known gaps

No acceptance run has happened yet. The rules below say what the run must show; every status on this page stays partial until it does.

  • Scope: every chunk size. The acceptance suites run at each chunk size the model configuration allows, fixed at server startup: 80, 160, 320, 560 and 1120 ms for the Nemotron streaming model. Chunk size sets encoder lookahead, so each size is a different workload. 320 ms is the default configuration, not the only size (ACC-001, ACC-002, ACC-004).
  • Target 1, the acceptance criterion: parity with the state-pool build. At each chunk size, the latency bound is the state-pool build's own p99 final latency at 32 sessions, measured first in the same run, so that build meets the bound at 32 by construction. Run-to-run noise is the spread between two repetitions of that build. The state layer must stay within the bound at 32, then each build's capacity is swept upward from 32 and the state layer's capacity must be no lower. At each shared concurrency point its p50 and p99 final latency and p50 and p99 time to first segment must be no worse, beyond noise, and its state memory per held session no worse (ACC-003). Missing a bound does not stop the run; the run records the distance.
  • Target 2, later: latency parity with NVIDIA's streaming ASR NIM on A100. NVIDIA publishes, for the Nemotron en-US row on a DGX A100 40 GB at 160 ms chunks and 128 streams, a mean latency of 67.9 ms and a p99 of 432.4 ms (NIM ASR performance table). It publishes no time to first segment, and this project has not measured the NIM. The two sets of figures differ in GPU, concurrency, workload and latency definition, so they are not comparable yet. This target sits on the Future roadmap; it is not an acceptance criterion.
  • Pool sizing (DECL-014). The state page pool takes the KV cache budget that profiling leaves, as upstream sizes a pure-Mamba model, with no separate state budget and no fixed page count. The existing startup check refuses a budget below one page per active row.
  • Fixed page address (PRES-009, ACC-008). A held request keeps the same block id and device address in each state group across turns, parking, folds and compaction; the pool takes the page back only at the terminal finish. A graph captured once can then address the page by block id.
  • State-group layout accessor (PREP-009). Before graph capture, core gives the model state a read-only view of each state group's tensors: backing tensor, dtype, per-page shape and page stride. The plugin's transaction graphs need it (ACC-006).
  • Execution modes (DECL-006, ACC-005, ACC-007). Core accepts async scheduling, runner CUDA graphs under PIECEWISE, FULL, FULL_DECODE_ONLY and FULL_AND_PIECEWISE, torch.compile, and batch-invariant mode. Each needs a test: graph replay over rows that hold different pages must match an eager run, and output token ids must not depend on batch composition.

13 · Requirements

The nine requirements (PF-1 to PF-9)

Each requirement states an outcome. The text is the requirements document's Generic feature requirements table as it stood on 2026-11-23.

ID and nameRequirement
PF-1 DeclareA model declares each state component (shape, dtype, initial value), that its inputs cannot rebuild it, its tensor-parallel ownership, and which history it needs to continue: positions, if it reads them; past output, if its sampling params read it. It also declares its startup prerequisites: whether it captures its own graphs, what that capture needs, and which synthetic warmup inputs it accepts.
PF-2 PreserveA request holds its state exclusively from first schedule until it finishes by any path. Core performs no operation that loses, duplicates or rebuilds it (preempt, evict, recompute, prefix-share, cache reset, sleep), and the storage, layout and addressing a graph captured stay valid until that graph is retired, or the graph is invalidated and recaptured before its next replay.
PF-3 Bound the pageA new page holds its declared initial value before its first read. A page is reused only after every access by its previous owner is ordered before the new owner's first access, on every finish path.
PF-4 Exactly onceCommitted input changes state once and in order. Nothing else changes it: not a sample after a stop, a resume replay, a warmup or profiling input, or input cancelled before it ran. Profiling, warmup and capture neither change nor read live state.
PF-5 Turn boundaryA request parks only at a stop the model declares resumable; any other end (abort included) finishes it. A model may declare its per-turn max_tokens stop resumable, as resident sessions (#68539) need. A stop at the position limit always ends the stream. Under the per-request barrier no watermark is needed: the fold discards the turn's last sampled token, and no step runs past the stop.
PF-6 Length independencePer-turn work, transfer and retained host memory in every engine layer are O(new input): scheduler request, output processor, original payloads, encoder features and the pending-input queue.
PF-7 Account and reclaimAdmission counts every resource a live request holds, running or parked, and refuses at open when one is exhausted. Every held resource returns to free when its caller closes or aborts the stream; the engine core sets no deadline, and the frontend aborts a stream whose input or output side ends early.
PF-8 Fail one requestA failure attributable to one request, reported by the model or forced by PF-2, finishes that request with an error; every other request continues. The rule defines what a partial write leaves in the page and which completion the failure belongs to. Arbitrary Python or CUDA exceptions stay fatal.
PF-9 Start and resume safelyCore honors a model's declared profiling, warmup and capture prerequisites, so a model may decline synthetic inputs it does not support in favour of a supported preparation path, and counts retained allocations and transient peaks before final page sizing. Before serving after startup, wake or cache reset, core makes the required execution resources and graphs ready and consistent with PF-2 to PF-4.
