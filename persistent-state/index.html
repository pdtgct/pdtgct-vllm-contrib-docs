vLLM review guide · status 2026-11-27

Engine-managed persistent state for streaming models

vLLM keeps state that it can rebuild from tokens. A growing set of streaming audio, speech and video models carry state that comes from their input and cannot be rebuilt. Three RFCs add that capability in small, opt-in steps. This page explains the gap, lists the models that need the capability, and walks through each pull request in the order we ask you to review it. A maintainer's guide to the landscape carries the detailed analysis.

1 · The gap

vLLM can rebuild every piece of state it keeps. Streaming models need state it cannot rebuild.

The KV cache stores keys and values by token position. If the engine drops a block, it rebuilds the block by replaying the retained tokens. Mamba-style models keep fixed-size convolution and recurrent state, but that state also derives from the token prefix, and vLLM rebuilds it the same way. Both mechanisms live within one request.

A cache-aware streaming ASR model such as Nemotron 3.5 ASR Streaming carries encoder attention and convolution caches, predictor state and decoding progress from one audio chunk to the next. That state derives from audio that the server no longer holds. The transcript cannot reconstruct it. The engine must keep the state resident between the inputs of a stream. It must also order every access by a page's previous owner before the next owner's first access, because a late write would otherwise land in the next session's state.

KV cache

  • Keys and values by token position
  • Grows with the sequence
  • Rebuilt by replaying retained tokens
  • Prefix-shared across requests

Mamba state

  • Fixed-size convolution and recurrent tensors
  • Derived from the token prefix
  • Rebuilt by replaying the prefix
  • Lives for one request

Persistent state (RFC 1)

  • One fixed-size page per session, in a Mamba-style group marked not rebuildable
  • Derived from input audio, so no replay exists
  • Admitted with the opening request; kept between inputs
  • Reused only after the previous owner's accesses are ordered

4 · Merge order

What to review first

The order follows what each serving stage needs. Steps 1, 2 and 3 do not depend on each other, so different reviewers can take them in parallel.

  1. #67144, then #67151. Two speech-to-text fixes, 93 source lines together. Stage 1 needs #67151: without its two request fields, the model cannot refuse beam search.
  2. #67583, then the state-layer pull request. The six model hooks come first; the current plugin release requires them to capture its own CUDA graphs. The state-layer pull request is the core of stage 1. It has not opened; until it does, review the design on the nine requirements and the branch named under RFC 1.
  3. #65546, then #67294. Endpoint plugin start, stop, readiness and drain. These are the core of stage 2. A frontend plugin works with #65546 alone; #67294 adds /ready and coordinated draining.
  4. #67139. An independent fix that refuses new /v1/realtime sessions during shutdown. Merge it at any time.
  5. vllm#65549, then vllm-omni#9849. RFC 3. Only vLLM-Omni serving depends on them.

5 · RFC 1 · vllm#65543

Persistent state as a state layer, with nine rules

Core owns the state's lifetime: allocation, admission, scheduling and safe reuse. The model, in an out-of-tree plugin, owns the computation and the layout. The design has two parts.

Storage. Lucas Wilkinson's draft pdtgct/vllm#6 ("PR 6") puts each session's state in a Mamba-style group that the normal KV cache allocator owns, a MambaSpec group with recomputable=False. Its core change is +34 / −4 lines under vllm/. A resumed session continues through the upstream streaming-input fold.

Lifecycle. Nine requirements state what core must add so that state it cannot rebuild survives every path through the engine. The landscape guide gives their full text.

ID and nameOutcome
PF-1 DeclareThe model declares each state component, that inputs cannot rebuild it, the history it needs and its startup prerequisites.
PF-2 PreserveCore never preempts, evicts, recomputes, prefix-shares, resets or sleeps away held state, and keeps captured graph addresses valid.
PF-3 Bound the pageA new page holds its initial value before its first read; reuse waits until the previous owner's accesses are ordered.
PF-4 Exactly onceCommitted input changes state once and in order; warmup, profiling and capture neither change nor read live state.
PF-5 Turn boundaryA request parks only at a stop the model declares resumable; any other end finishes it.
PF-6 Length independencePer-turn work and retained host memory in every engine layer are O(new input).
PF-7 Account and reclaimAdmission counts every held resource and refuses at open; the caller owns the stream's lifetime, and the engine core sets no deadline.
PF-8 Fail one requestA failure the model reports for one request, or a PF-2 violation, finishes that request with an error; the others continue. Other Python or CUDA exceptions still stop the engine.
PF-9 Start and resume safelyCore honors the declared profiling, warmup and capture prerequisites before final page sizing and before serving.

The implementation is pdtgct/vllm branch pstate-impl-20261122, tag pstate-impl-head, head 9503e3b878: upstream main 842f74fa8d plus PR 6's net diff, the hooks-only re-cut of #67583 and a fix for #69139. Against that main it adds +1,785 / −86 lines under vllm/ in 34 files, and 9,592 lines of tests. Core meets PF-1 to PF-8 in code and tests; for PF-9 it has the state-group layout accessor and graph capture over block 0. Production design maps each gap found in the PR 6 proof of concept to its rule.

The first consumer is the out-of-tree plugin vllm-nemotron-asr-streaming-plugin. Sohaib Ahmad's #59827 added complete-audio transcription for the same checkpoint; the plugin adds streaming sessions, and serves complete files on the same server.

History. RFC 1 first proposed a separate state pool with its own scheduler, in #67374 and #67375, about 1,500 source lines each, with the model hooks stacked on them in #67583. The state layer replaced it on 2026-11-21. State pool vs state layer explains why, and Streaming-session designs compares both with resident sessions in #68539 and bounded sessions in #53879.

6 · RFC 2 · vllm#65545

Lifecycle hooks for endpoint plugins

An endpoint plugin can register routes, but core never tells it when the server starts accepting traffic or begins to shut down. A plugin that holds long-lived connections, such as a gRPC listener or a WebSocket session, has no point at which to drain before the engine stops. RFC 2 adds that point for any endpoint plugin, not for one model.

The pull requests follow the RFC review: typed Protocols, /health unchanged, a separate readiness endpoint, isolated drains, and two stages. The realtime shutdown bug that the review raised is a separate pull request, #67139.

#65546Endpoint plugin startup and cleanup hooksstage 2
Adds
Optional SupportsStart and SupportsStop Protocols. start runs in load order before HTTP accepts, with rollback on failure; stop runs in reverse order, isolated, with a deadline from VLLM_ENDPOINT_PLUGIN_STOP_TIMEOUT_SECONDS (default 5). Adds state.request_shutdown().
Who is affected
Plugins without start or stop are unchanged. Two changes reach every server: a repeated SIGINT or SIGTERM now exits once the engine has stopped, and a failed startup on Uvicorn below 0.50 exits with status 3 instead of 0.

8 · RFC 3 · vllm-omni#9848

vLLM-Omni on Model Runner V2, consuming the core interfaces

RFC 3 replaces an earlier Omni-only design that changed code at nearly every level of vLLM-Omni. A reviewer advised that ASR state belongs in vLLM core on MRv2, and RFC 1 follows that advice. RFC 3 keeps only multi-stage orchestration and inter-stage transfer in vLLM-Omni.

vllm#65549 adds GPUModelRunner._init_model_state() (+11 / −3 in model_runner.py), so an MRv2 runner subclass can supply its own ModelState without patching a module-level factory. The default method calls the same factory with the same arguments. vllm-omni#9849 overrides it in OmniGPUModelRunner. Both are ready for review and mergeable.

The landscape guide shows how the RFC 1 rules meet vLLM-Omni full duplex through an engine-core contract that holds for every engine-core client.

Known limits. A server that takes whole files keeps the max_model_len its longest file needs (77,000 for 600 s) and pays a raised token budget: on an A40 at 320 ms, state pages fell from 6170 to 2742 eager and from 6441 to 2885 with CUDA graphs. The landscape attributes that loss. On an earlier integration build, a whole-file request in flight also slowed concurrent streams: eight streams' p95 final latency rose from 0.55 s to 3.64 s with one 293 s file in flight.
