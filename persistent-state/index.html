Engine-managed persistent state for streaming models

vLLM keeps state that it can rebuild from tokens. A growing set of streaming audio, speech and video models carry state that comes from their input and cannot be rebuilt. Three RFCs and ten pull requests add that capability in small, opt-in steps. This page explains the gap, lists the models that need the capability, and walks through each pull request in the order we ask you to review it.

1 · The gap

vLLM can rebuild every piece of state it keeps. Streaming models need state it cannot rebuild.

The KV cache stores keys and values by token position. If the engine drops a block, it rebuilds the block by replaying the retained tokens. Mamba-style models keep fixed-size convolution and recurrent state, but that state also derives from the token prefix, and vLLM rebuilds it the same way. Both mechanisms live within one request.

A cache-aware streaming ASR model such as Nemotron 3.5 ASR Streaming carries encoder attention and convolution caches, predictor state and decoding progress from one audio chunk to the next. That state derives from audio that the server no longer holds. The transcript cannot reconstruct it. The engine must keep the state resident between the inputs of a stream. It must also hold the memory until every GPU write to it has finished, because a late write would otherwise land in the next session's state.

KV cache

  • Keys and values by token position
  • Grows with the sequence
  • Rebuilt by replaying retained tokens
  • Prefix-shared across requests

Mamba state

  • Fixed-size convolution and recurrent tensors
  • Derived from the token prefix
  • Rebuilt by replaying the prefix
  • Lives for one request

Persistent state (RFC 1)

  • One fixed-size page of model-declared tensors per session
  • Derived from input audio, so no replay exists
  • Reserved before the first input; kept between inputs
  • Reusable only after the worker acknowledges the last write

3 · The change set

Ten pull requests, each with a narrow source change

Each RFC lands as a short stack of pull requests. A stacked pull request lists its own commits, and you review only those. Most of each change is tests and design documentation.

5 · RFC 1 · vllm#65543

Scheduler-owned persistent state

Core owns the state's lifetime: allocation, admission, scheduling and safe release. The model, in an out-of-tree plugin, owns the computation and the layout. A model declares its page with PersistentStateSpec (tensor shapes, element types, offsets, alignment and initial values). Core allocates the pages from the existing block pool, and the worker exposes typed views of them.

The first consumer is the out-of-tree plugin vllm-nemotron-asr-streaming-plugin. Sohaib Ahmad's #59827 added complete-audio transcription for the same checkpoint; the plugin adds streaming sessions, and serves complete files on the same server.

#67374State pool, scheduling and release fencestage 1
Adds
A fixed GPU pool of per-request state slots, sized max_num_seqs + 1. StateScheduler, a subclass of Scheduler, binds one slot to a request across steps and across stream inputs. The release fence returns a slot only after the worker's completion event covers the request's last step and cleanup.
Review
One commit. New files vllm/v1/core/sched/state_scheduler.py and vllm/v1/worker/gpu/state_slots.py; design in docs/design/persistent_state.md.
Who is affected
Only models that declare supports_persistent_state = True. The pool and StateScheduler exist only when the KV cache layout holds a persistent-state group. Other engines get no-op scheduler hooks and new wire fields with defaults.

6 · RFC 2 · vllm#65545

Lifecycle hooks for endpoint plugins

An endpoint plugin can register routes, but core never tells it when the server starts accepting traffic or begins to shut down. A plugin that holds long-lived connections, such as a gRPC listener or a WebSocket session, has no point at which to drain before the engine stops. RFC 2 adds that point for any endpoint plugin, not for one model.

The pull requests follow the RFC review: typed Protocols, /health unchanged, a separate readiness endpoint, isolated drains, and two stages. The realtime shutdown bug that the review raised is a separate pull request, #67139.

#65546Endpoint plugin startup and cleanup hooksstage 2
Adds
Optional SupportsStart and SupportsStop Protocols. start runs in load order before HTTP accepts, with rollback on failure; stop runs in reverse order, isolated, with a deadline from VLLM_ENDPOINT_PLUGIN_STOP_TIMEOUT_SECONDS (default 5). Adds state.request_shutdown().
Who is affected
Plugins without start or stop are unchanged. Two changes reach every server: a repeated SIGINT or SIGTERM now exits once the engine has stopped, and a failed startup on Uvicorn below 0.50 exits with status 3 instead of 0.
Review state
The Claude review bot reported "Nothing blocking" on 2026-11-16, at a maintainer's request. No human review yet.

7 · Bug fixes

Three speech-to-text fixes, found while serving streaming ASR

Each fix applies to every speech-to-text user, not only to persistent-state models.

Pull requestTodayWith the fixSource lines
#67144
Fail requests that finish with error or abort		 A transcription that ends with error or an engine abort returns HTTP 200 with a partial transcript. error returns 500 and abort returns 503. The handler cancels sibling chunks of long audio. length and repetition still return 200. 26

8 · RFC 3 · vllm-omni#9848

vLLM-Omni on Model Runner V2, consuming the core interfaces

RFC 3 replaces an earlier Omni-only design that changed code at nearly every level of vLLM-Omni. A reviewer advised that ASR state belongs in vLLM core on MRv2, and RFC 1 follows that advice. RFC 3 keeps only multi-stage orchestration and inter-stage transfer in vLLM-Omni.

vllm#65549 adds GPUModelRunner._init_model_state() (+11 / −3 in model_runner.py), so an MRv2 runner subclass can supply its own ModelState without patching a module-level factory. The default method calls the same factory with the same arguments. vllm-omni#9849 overrides it in OmniGPUModelRunner. Both stay drafts until vLLM-Omni catches up with vLLM main.

Measured on a stage 1 build with the first consumer

The stage 1 build is vLLM main with the RFC 1 pull requests, #67144 and #67151 merged on a fork branch (hook-build-20261114b at 9c40a6ffd6). On one NVIDIA A40 at FP32, with the plugin's default 320 ms lookahead, CUDA graphs captured through #67583's hooks, and --max-num-seqs 64:

LibriSpeech test-clean and test-other over core's /v1/realtime5,55932Every session ended stop. WER 3.57 % (test-clean) and 7.99 % (test-other).
LibriSpeech test-clean64064Every session reached a final transcript. WER 2.89 %.

The server logged no preemption and no error. The plugin's README lists each result with its tier, build and plugin revision. Its quick start reproduces both serving stages with one vllm serve command each. Stage 2 adds the vllm-riva-frontend endpoint plugin on a build that also carries #65546 and #67294.

Known limit: a whole-file request in flight slows concurrent streams on the same server. On an earlier integration build, eight streams' p95 final latency rose from 0.55 s to 3.64 s with one 293 s file in flight.
